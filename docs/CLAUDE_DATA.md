# القسم أ — إدارة الحالة البرمجية (State Management)

- استخدم كلاسات **Cubit/Bloc** لإدارة حالات الميزات والتطبيق ككل — يُمنع منعاً باتاً استخدام Riverpod أو Provider أو GetX.
- يجب أن تعتمد الكيوبيتس (Cubits) **فقط وحصرياً على الـ Use Cases** — يُمنع تماماً أن تتصل الكيوبيتس مباشرة بالمستودعات (Repositories) أو مصادر البيانات (Data sources).
- يُسمح باستخدام الـ `setState` **فقط وحصرياً لحالات الواجهة المحلية البسيطة جداً** (مثل إظهار/إخفاء عنصر، التركيز على حقل إدخال) — ويُمنع نهائياً استخدامها لإدارة منطق الأعمال (Business Logic).
- يجب إبقاء نطاق استخدام الـ `setState` ضيقاً ومحصوراً في أصغر ودجت ممكنة لتجنب عمليات إعادة البناء غير الضرورية لشجرة الودجتس.

# القسم ب — حظر وتقييد توليد الأكواد (Limited Code Generation)

- **لا تستخدم أداة Freezed نهائياً.** استخدم مميزات لغة Dart 3+ المدمجة بدلاً منها:
  - كلاسات اتحادية مغلقة (`sealed class`) لإدارة حالات الـ Bloc/Cubit مع استخدام exhaustiveness مطابقة الأنماط (Pattern Matching).
  - تعبيرات `switch` والـ records للتعامل مع هياكل البيانات خفيفة الوزن.
- **الأدوات المسموحة فقط**: حزمتي `Flutter Gen` (لإدارة الأصول والصور) و `Retrofit` (لإنشاء عملاء الـ API) هما الأدوات **الوحيدة والمصرح بها** لإنشاء وتوليد الأكواد بالتطبيق.
- *ملاحظة: أي ملفات قديمة تستخدم Freezed يجب إعادة صياغتها وتحويلها إلى كلاسات Dart Native مغلقة عند تعديلها.*

# القسم ج — نقاء طبقة الدومين (Domain Layer Purity)

- يجب أن تكون طبقة الدومين نقية وخالية تماماً من أي استيراد يخص فلاتر. يُمنع نهائياً وجود استيراد `package:flutter/...` في أي ملف يقع تحت مجلد `domain/`.
- **قاعدة التمرير البسيط (Pass-through Rule)**: إذا كانت طبقة الدومين (Use Cases) تعمل كمجرد ممر بسيط يقوم فقط بتمرير البيانات إلى المستودعات دون إضافة أي منطق أعمال أو تحقق أو تنظيم، فيجب **حذف طبقة الدومين والـ Use Cases لهذه الميزة فوراً**، وتخفيض معمارية الميزة لتصبح ثنائية الطبقات (Tier 2: presentation & data) لتبسيط الكود وتجنب التعقيد غير المفيد.

# القسم د — حقن الاعتماديات (Dependency Injection)

- استخدم حزمة **`get_it`** كمحدد للخدمات (Service Locator) لحقن وحل الاعتماديات — يُمنع نهائياً استخدام Provider أو الحقن عبر الباني يدوياً خارج نظام الحقن.
- يجب تسجيل جميع الاعتماديات داخل ملف إعداد موحد `core/di/` (أو دوال التهيئة المحددة للميزات).
- يتم جلب الـ Cubits، الـ Use Cases، والـ Repositories عبر الـ `get_it` (الوسيط `sl<Type>()`)، ويُمنع نهائياً إنشاؤها يدوياً باستخدام كلمة `new` أو الباني المباشر.

# القسم هـ — قواعد وعقد معالجة الأخطاء (Error Handling Contract)

- **طبقة البيانات (Data Layer)**: يجب التقاط جميع الاستثناءات (Exceptions) عند حدود هذه الطبقة وتحويلها وتمريرها في كلاسات الـ `Failure` المحددة باستخدام معالج الأخطاء المركزي. لا تقم نهائياً برمي استثناءات خام (raw exceptions).
- **طبقة الدومين (Domain Layer)**: يجب أن تقوم الـ Use Cases والـ Repositories بإرجاع كائن من نوع `ApiResult<T>` لتمثيل النجاح أو الفشل بشكل مغلق وآمن.
- **طبقة العرض (Presentation Layer)**: يجب مطابقة ومعالجة كائنات الـ `Failure` وتحويلها إلى رسائل واضحة ومحببة للمستخدم تظهر في الواجهة بناءً على الثوابت المركزية.
- **الـ Logging الموحد**: استخدم دائماً نظام التسجيل المركزي `AppLogger` لتسجيل جميع الأخطاء البرمجية (حيث تظهر في الكونسول أثناء التطوير، وترسل إلى Crashlytics في مرحلة الإنتاج) — يُمنع استخدام `print()` أو `debugPrint()`.
- **سياسة الالتقاط**: قم بالتقاط الأخطاء عند الحدود الخارجية القصوى فقط (Outermost boundary) — ولا تقم ببلع الأخطاء أو كتمانها داخل الدوال الداخلية العميقة.

# القسم و — تفصيل معالجة الأخطاء (Error Handling Deep Dive)

## مخطط تدفق الأخطاء والبيانات (Error Flow Diagram)

```
خطأ في الشبكة أو الـ API
    ↓
[طبقة البيانات] التقاط الـ DioException ← تحويلها عبر المعالج المركزي ← كائن Failure محدد النوع
    ↓
[المستودع Repository] يقوم بتغليف النتيجة وإرجاع ApiResult.failure(failure)
    ↓
[الـ Use Case] يمرر كائن ApiResult<T> كما هو دون أي تغيير
    ↓
[الـ Cubit] يقوم بمطابقة الأنماط (Pattern Matching) للـ ApiResult ← إصدار حالة الواجهة المناسبة
    ↓
[الـ Widget] يعرض شاشة الخطأ برسالة واضحة للمستخدم مأخوذة من النصوص المركزية
```

## هرمية الأخطاء المغلقة (Failure Hierarchy - Sealed Class)
```
Failure (sealed)
├── ServerFailure       ← خادم الـ API أرجع رمز فشل غير ناجح (Non-success status code)
├── NetworkFailure      ← لا يوجد اتصال بالإنترنت / انتهت مهلة الاتصال / خطأ اتصال
├── CacheFailure        ← فشل قراءة أو كتابة البيانات في التخزين المحلي (Local Storage)
├── LocationFailure     ← فشل في الـ GPS أو تحديد الموقع الجغرافي
├── SensorFailure       ← البوصلة أو حساسات الجهاز غير متوفرة
├── WrongPasswordFailure ← خطأ في كلمة المرور أو المصادقة
├── MissingDataFailure  ← البيانات المطلوبة غير موجودة
└── UnknownFailure      ← خطأ غير متوقع (Catch-all)
```

# القسم ز — قائمة افعل ولا تفعل للبيانات والمنطق (Data & Domain Do's & Don'ts)

## ✅ افعل (DO)
- **DO** اتبع بصرامة حدود المعمارية ثلاثية الطبقات المعتمدة (Presentation -> Domain -> Data).
- **DO** استخدم الكيوبيتس حصرياً لإدارة وتخزين حالة الميزة.
- **DO** أرجع دائماً كائن من نوع `ApiResult<T>` من المستودعات والـ Use Cases.
- **DO** قم بتسجيل الاعتماديات والكيوبيتس والخدمات عبر الـ DI الموحد باستخدام `sl<Type>()`.
- **DO** استخدم نظام التسجيل المركزي `AppLogger` لجميع عمليات الـ Logging والأخطاء.
- **DO** قم ببلورة وتجهيز البيانات وتعديلها (String formatting, Regex parsing) داخل الـ Models في طبقة البيانات قبل تمريرها للـ UI.

## ❌ لا تفعل (DON'T)
- **DON'T** تقم بإضافة استيراد يخص مكتبات فلاتر داخل مجلد الـ `domain/` نهائياً.
- **DON'T** تقم بإنشاء أو تفعيل أي كلاس Cubit أو Repository أو Service يدوياً خارج نطاق الـ DI.
- **DON'T** ترمِ استثناءات خام (raw exceptions) من المستودعات أو مصادر البيانات نهائياً.
- **DON'T** تقم ببلع الأخطاء أو التغاضي عنها دون إبرازها وتمريرها للمستخدم لتجنب توقف التطبيق بصمت.
- **DON'T** تضع أي منطق أعمال أو تحقق أو حسابات معقدة داخل شاشات الـ UI.
- **DON'T** تستخدم أي مكتبات إدارة حالة خارجية غير الـ Cubit/Bloc.
- **DON'T** تستخدم حزمة `Freezed` لتوليد المودلز أو الحالات، واستبدلها بمميزات Dart 3 Native.
- **DON'T** تقم بتسجيل بيانات حساسة تخص المستخدم (مثل إحداثيات الموقع أو معلومات الجهاز) في خوادم الإنتاج.
